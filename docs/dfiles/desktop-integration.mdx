# Desktop Integration

## Reveal in File Manager

While it runs, Dux Files owns `org.freedesktop.FileManager1` on the session bus, so `ShowFolders`, `ShowItems` and `ShowItemProperties` calls from other apps land here. Browsers built on Chromium ask the desktop portal's `OpenDirectory` when a portal runs, and the portal forwards that to `ShowItems`.

Dux Files never takes the name from another file manager. It waits in the queue until that one quits. **Settings → General → Register as the session file manager** stops a running Dux Files from asking for the name at all.

`make install` and the distribution packages also install `dev.duxlabs.files.FileManager1.service`, so a call can start Dux Files when nothing owns the name. An instance started that way serves the call whatever the setting says, and quits if it never opens a window (for example when the call named a missing file).

:::note

Nautilus, Dolphin, Thunar and Nemo ship activation files for the same name. `dbus-daemon(1)` gives the first service directory precedence (the default `PREFIX=/usr/local` puts ours ahead of `/usr/share`) and calls the choice arbitrary inside one directory. If another file manager keeps winning, remove its activation file or install Dux Files under a prefix that sorts first.

:::

## Default File Manager

```bash
xdg-mime default dev.duxlabs.files.desktop inode/directory
```

The desktop entry also claims `trash`, `sftp` and `smb` URIs and the archive types Dux Files can extract, so you can make it the default for those the same way.

## Open and Save Dialogs

Dux Files can serve `org.freedesktop.impl.portal.FileChooser`, the backend side of the desktop portal's file chooser. Apps that ask the portal for files then get a Dux Files window with the same sidebar, bookmarks, search and keys as the file manager:

- Flatpak apps
- Chromium browsers
- Firefox with `widget.use-xdg-desktop-portal.file-picker` set to `1`
- GTK 4 apps under `GDK_DEBUG=portals`
- Qt apps under `QT_QPA_PLATFORMTHEME=xdgdesktopportal`

Apps that draw their own dialogs are unchanged. When the calling app hands the portal its window, the dialog becomes a child of it: through xdg-foreign-v2 on Wayland, as a transient dialog on X11. In a Wayland session, apps running under XWayland pass an X11 window, which a Wayland client cannot use, so their dialog is a standalone window. The `modal` option is ignored.

### Turning it on

Nothing is switched on by install. The packages ship `dfiles.portal` and its activation file, but the choice of backend is per user, in `~/.config/xdg-desktop-portal/<desktop>-portals.conf`. Two ways to flip it:

- **Settings → General → Use Dux Files for open and save dialogs**
- `dfiles portal install`

Both write the per-user files when the packaged ones are missing, put `dfiles` first in the `org.freedesktop.impl.portal.FileChooser` key (keeping the previous backend as the fallback and every other line as it was), and record what changed so **Restore** or `dfiles portal uninstall` puts it back. `dfiles portal status` shows each part.

xdg-desktop-portal reads its configuration once at startup, so the change takes effect after:

```bash
systemctl --user restart xdg-desktop-portal.service
```

The UI and the CLI ask before doing that, because the restart cancels file dialogs other apps have open.

### How it starts

The portal activates the backend on demand through the activation file. Without the systemd user unit that means one hidden start of Dux Files whenever xdg-desktop-portal starts (it quits again after 30 s with nothing to show) and a cold start for the first dialog. With the unit, the resident instance answers at once. See [Running at Login](installation#running-at-login).

### Floating the dialog

niri and sway open child windows floating, so a dialog with a Wayland parent floats with no rule. A dialog without a parent needs one.

The open, save and select folder dialogs use the app id `dev.duxlabs.files.chooser`. The file manager keeps `dev.duxlabs.files`, so a rule can match the dialogs alone, whatever title the calling app asked for.

niri:

```kdl
window-rule {
    match app-id=r#"^dev\.duxlabs\.files\.chooser$"#
    open-floating true
}
```

Hyprland:

```lua
hl.window_rule({ match = { class = "^(dev\\.duxlabs\\.files\\.chooser)$" }, float = true })
```

:::note

In 2.1.2 and older the dialogs share `dev.duxlabs.files` with the file manager and can only be told apart by title. A rule anchored to that id, like the one this page used to show, stops matching the dialogs after the change. Replace it with the rule above.

:::

### Packaging and Nix

Packagers install `dfiles.portal` under `share/xdg-desktop-portal/portals/` and the service file under `share/dbus-1/services/` with the binary path substituted, and do not ship a `portals.conf` that prefers it. On NixOS and home-manager, `programs.dux-files.portal.enable` registers the backend and `portal.preferred` writes the preference. See [NixOS Installation](nixos-flake).

The Flatpak cannot register the backend: Flatpak exports no `share/xdg-desktop-portal` files.

## Lifetime

The systemd user unit starts Dux Files with `--keep-running`, so the close button hides the last window there. Started any other way, closing the last window quits unless **Settings → General → Close behavior** says to keep running.

## Theme

Dux Files follows [Dux Modular Shell](../dms/overview)'s colors when **Settings → Appearance → Color source** is **Auto** and Dux Modular Shell runs. Pick **Preset** for a bundled palette or **Custom** for your own theme file. Light and dark follow the desktop portal's color scheme setting.
